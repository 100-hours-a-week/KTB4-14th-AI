# 추억영상 품질 목표와 GPU 처리 용량

작성일: 2026-11-01. 대상은 기본 `ltx23_film` 경로다. **관측값**, **현재 필터 기준**, **출시 목표**를 구분한다. 한 앨범의 통과나 모델의 confidence를 서비스 품질 보증으로 해석하지 않는다.

## GPU 한 대와 N명의 사용자

동시 요청 접수 수와 동시에 실행하는 GPU 추론 수는 다르다. 기본 ComfyUI 프로세스는 하나의 `prompt_worker`가 큐에서 워크플로를 꺼내 실행한다([공식 구현](https://github.com/Comfy-Org/ComfyUI/blob/master/main.py)).

현재 실행기는 장면별 워크플로를 제출하고 완료를 기다린 뒤 다음 장면을 제출한다. 여러 영상 작업을 동시에 호출하면 각 작업의 장면이 ComfyUI 큐에 섞일 수 있다. 이는 여러 영상을 동시에 GPU 추론한다는 뜻이 아니다. RunPod 주소 탐색의 lock과 사진 분석의 semaphore도 GPU 작업 수 제한이 아니다.

현재 영상 기능은 Python/CLI다. 사용자별 영속 대기열, 접수 상한, 공정한 스케줄링, 대기시간 추정, 중복 요청의 소유권 관리는 아직 HTTP/SQS 영상 계약으로 구현하지 않았다. 기존 여행 일정 SQS 소비자가 영상 메시지를 처리한다고 가정하면 안 된다. ComfyUI의 메모리 큐만으로 서비스 작업의 내구성·중복 방지·사용자 권한을 보장하지 못한다.

권장 운영 구성은 **영상 요청 → 영속 작업 저장소/대기열 → GPU당 한 개의 소비자 → 결과 저장소**다. 영상과 자동 작곡이 같은 GPU를 쓴다면 같은 실행 한도를 공유해야 한다. 상태는 `QUEUED/RUNNING/RETRYING/COMPLETED/FAILED`로 구분하고 다음을 함께 구현한다.

- 접수 시 작업 ID와 멱등 키를 저장하고, 사진·작업·결과 접근 권한을 사용자별로 확인한다.
- GPU별 소비자 동시 실행 수는 우선 1로 둔다. 재시작·중복 수신에는 작업 lease/heartbeat와 제출한 prompt ID를 이용한다. 제출 응답 유실 시 무조건 재전송하지 않는다.
- SQS를 사용한다면 장시간 작업 중 visibility timeout을 갱신하고, 실패 횟수 제한과 DLQ를 둔다. 영구 저장소에 상태를 남긴다.
- 대기열 길이/예상 대기시간에 따라 접수 상한을 둔다. 웹 요청 하나를 수십 분 열어 두는 방식으로 운영하지 않는다.
- 다른 GPU가 준비되면 소비자를 늘려 처리량을 확장한다. 같은 GPU에서 추론 수를 2 이상으로 올리는 것은 VRAM과 부하 시험을 통과한 뒤 결정한다.

영상 한 편의 전체 서비스 시간(재시도·검수·편집 포함)을 `T`초라고 할 때, FIFO로 직렬 처리하는 단순 구성의 처리량은 약 `3600/T`편/시간이다. 같은 길이의 N개 작업이 동시에 도착하면 마지막 완료는 대략 `N×T` 뒤다. 실제로는 캐시, 준비 시간, CPU/API 병렬화와 실패에 따라 달라진다. **12초 소스 한 개의 추론 시간으로 완성 영상의 T를 대체하지 않는다.**

현재 N>1 부하 시험, GPU 최대 메모리, OOM률, 서비스 p50/p95는 미측정이다. 따라서 “한 GPU가 동시에 N명까지 보장한다”는 수치는 아직 없다. 기존 `report.total_seconds`도 모든 실패 실행과 최종 대체 편집을 포함한 end-to-end 시간이 아니므로 운영 SLA의 근거로 사용하지 않는다.

## 품질 목표

아래 출시 목표는 제안 기준이다. 현재 코드가 모든 목표를 강제하거나 달성했다는 뜻이 아니다.

| 지표 | 정의/측정 | 제안 목표 | 현재 적용/한계 |
|---|---|---|---|
| 길이 정확도 | 실제 디코딩 프레임 수와 요청 길이×fps 차이 | 1프레임 이하 | 정확한 정수 프레임 편집. 실제 파일도 별도 디코딩해 확인 |
| 생성 소스 재사용 | `(컷 수−서로 다른 생성 소스 수)/컷 수` | 0% | 같은 소스/scene key 재사용 거부. 다른 파일의 유사 장면까지 판별하는 지표는 아님 |
| 장면 다양성 | 서로 다른 기억 단위 수, 단위별 화면 점유율, 사람의 반복 평가 | 30초·충분한 적격 기억이 있으면 10–15장면, 한 기억 점유율 ≤20% | 선택 단계 최대 15. 실패 후 축소 시 현재 7장면도 가능하므로 목표 미달을 별도 표시해야 함 |
| 정지 구간 | 320px 폭·4Hz 샘플에서 MAD<0.55이고 광류 p90<0.035인 연속 구간 | 0.75초 미만; 초기 상한은 해당 전이의 40% 이하 | `QualityPolicy`의 휴리스틱. 정상적인 고정 카메라와 오류를 실제 앨범으로 교정해야 함 |
| 흐림 | 같은 분석 크기에서 Laplacian variance<8인 샘플 비율 | 초기 필터 상한 50%; 최종 지각 품질은 별도 평가 | 배경 보케와 주 피사체 흐림을 이미지 모델이 추가 판정. 분산값 증가만을 최적화하지 않음 |
| 원본 충실도 | 원본과 생성 구간을 비교한 새 전경 인물/주요 형태 변형 판정 | 최종 검수에서 중대 결함 0건; 불확실하면 제외 | 일반 장면 검수+독립 인물 검수. 6/8장 샘플 판정이므로 실제 결함률 0%를 증명하지 않음 |
| 음악 | 최종 AAC의 LUFS/true peak/채널/침묵 검사 | 기본 음량에서 -20~-14 LUFS, true peak≤-1dBTP; 의도하지 않은 무음 0건 | 작곡 음원 검사와 음량 정규화. 사용자 무음/음량 설정은 별도. 최종 인코딩 후 측정도 필요 |
| 추억·행복감 | 원본과 함께 본 사람의 1–5점 평가 | 평균≥4.0, 3점 미만 비율≤10% | 미측정. 움직임이나 모델 confidence로 대체할 수 없음 |
| 처리 속도 | 접수→다운로드 가능 시각, 대기/계획/생성/검수/편집 분리 | 30초 warm 작업의 p95≤5분을 제품 목표로 검토 | 현재 미달/미검증. 생성 횟수·해상도·재시도를 함께 줄이고 품질 회귀를 비교해야 함 |

OpenCV 종합 `score`는 후보 구간의 순위를 정하는 값이다. `score=1.0`은 품질 100점이나 결함 확률 0%가 아니다. 모델 confidence도 정확도나 사용자 만족도가 아니다. SSIM/PSNR로 원본과 비슷함만 높이면 정지 영상이 유리하므로 주 품질 목표로 삼지 않는다.

## 현재 앨범의 실제 비교

동일한 110장 샘플 앨범에서 만든 두 결과의 편집·미디어를 재측정했다. 이전 버전은 일부 소스를 사람이 선택한 구간으로 재사용했고, 새 기본 경로는 자동 선택과 구간 검수를 적용한다. 버전·구성·검수 방식이 함께 바뀌었으므로 특정 변경 하나의 인과 효과로 단정할 수 없다. 집계값과 파일 지문은 [측정 스냅샷](quality-baseline-2026-11-01.json)에 보관했다. 사용자 사진과 영상은 Git에 포함하지 않는다.

| 지표 | 이전 결과 v3 | 최신 결과 v4 |
|---|---:|---:|
| 컷 수 | 11 | 7 |
| 서로 다른 생성 소스 | 7 | 7 |
| 소스를 다시 사용한 컷 | 4/11 (36.36%) | 0/7 (0%) |
| 재사용 컷이 차지한 영상 길이 | 48.19% | 0% |
| 한 생성 소스의 최대 점유율 | 41.67% (12.5초) | 14.31% (약 4.29초) |
| 실제 디코딩 길이 | 720프레임/30초 | 720프레임/30초 |
| 출력 크기 | 1920×1080 | 1920×1080 |
| 독립 인물 검수 | 동일 방식 자료 없음 | 최종 7/7구간 통과; 새 전경 인물 flag 0건 |
| 정지/흐림 측정 | 동일 방식 자료 없음 | 최종 7구간의 샘플 정지·흐림 비율 각각 0, 최대 정지 연속 0초 |

v4에서 실제 참조 사진은 9장, 확산 생성 해상도는 **1024×576**이다. 1080p는 확대 출력이다. 최종 AAC 측정은 **-19.87 LUFS, -6.84dBTP, 스테레오 48kHz**였다. 사람이 청취한 만족도 점수는 없다.

반복을 줄였지만 서로 다른 소스 수는 여전히 7개다. 10–15장면 목표 달성으로 발표하면 안 된다. 일반 장면 검수에서 놓쳤던 원본에 없는 전경 인물 때문에 중간 9장면 결과는 거절했고, 독립 인물 검수를 추가한 뒤 문제가 있는 구간을 제외해 7장면으로 마무리했다. 최종 샘플 검사에서 flag가 없다는 사실은 미검출률이 0이라는 뜻이 아니다. 사용자 최종 수락도 아직 확인되지 않았다.

현재 설명할 수 있는 개선은 “생성 소스 재사용 컷 비율을 36.36%에서 0%로 줄이고, 한 소스 점유율을 41.67%에서 14.31%로 낮췄으며, 독립 인물 검수로 일반 검수의 누락 사례를 걸러냈다”까지다. 전체 사용자 만족도 향상, 상용 성공률, 5분 이내 제작은 아직 실측 근거가 없다.

## 다음 버전을 비교하는 방법

1. 실제 앨범을 최소 30개 준비해 5/10/100장 수준, 인물·음식·자연·야간·흐림·유사 사진이 섞이도록 한다. 동일 사용자의 연속 사진이 개발/검증 양쪽에 섞이지 않게 나누고, 검증 목록을 고정한다. 이 개수는 시작 계획이며 통계적 보증 표본 수가 아니다.
2. 같은 입력/길이/해상도/음량과 사전 고정한 여러 seed로 이전·새 버전을 짝지어 만든다. 실패한 요청도 분모에 포함한다. 생성 모델·샘플러·프롬프트·품질 정책·검수 모델 버전을 함께 기록한다.
3. 생성 구간별 기술 지표와 원본 충실도를 기록한다. 후보 통과율, 최종 제공률, 재생성률을 나눠 기록해 “모두 거절해서 품질이 좋아진 것”도 드러내야 한다. 사람이 결함을 표시한 샘플로 검수기의 미검출률/오거절률을 교정한다.
4. 버전을 가린 순서로 3명 이상이 원본 충실도/자연스러움/다양성/추억·행복감/음악 적합성을 각각 평가한다. 같은 앨범의 여러 장면을 독립 사용자 표본으로 계산하지 않는다. 앨범별 점수와 차이, 분포·신뢰구간·선호율을 보고한다. 평가자 수만으로 독립 앨범 표본 수가 늘지는 않는다.
5. 보조 자동 평가로 [VBench 공식 구현](https://github.com/Vchitect/VBench)의 subject/background consistency, temporal flickering, motion smoothness, dynamic degree, aesthetic/imaging quality를 검토한다. 이번 결과에서는 실행하지 않았다. 카메라 컷이 섞인 최종본 전체보다 각 연속 장면을 평가하고 동일 버전/설정으로 비교한다. 높은 정합성 점수와 충분한 움직임을 함께 보며, 단일 총점으로 추억 충실도를 대신하지 않는다.
6. warm/cold를 나누고 대기 사용자 1/2/5/10명에서 측정한다. 우선 GPU 추론은 1개로 유지하며, 요청 손실/중복/OOM/재시도/최대 VRAM/대기 p50·p95/전체 완료 p50·p95를 기록한다. 서비스 시간의 표본 수와 실패율도 함께 표기한다. 이 시험은 아직 수행하지 않았다.

임계값은 개발 앨범에서 조정하고 고정된 검증 앨범으로 회귀를 확인한다. 핵심 우선순위는 인물·장소 충실도와 실제 움직임을 보존하면서, 사용 가능한 서로 다른 장면의 통과 수를 늘리는 것이다. 최근 결과처럼 통과 수가 부족할 때는 성공률·장면 수·처리시간 사이의 손실을 보고하고 재생성 정책을 개선한다.

## 측정 명령

GPU나 외부 모델 호출 없이 기존 편집 보고서를 집계하고 실제 영상을 디코딩한다.

```bash
python -m scripts.video.evaluate --report /jobs/JOB/report.json \
  --reviews /jobs/JOB/final-fidelity-reviews.json \
  --video /results/final.mp4 --output /jobs/JOB/evaluation.json
```

`--report`에는 기존 `take-plan.json`도 사용할 수 있다. 검수 자료가 없으면 관련 값은 `null`이다. `--reviews`는 최종 take의 scene key·시작 프레임·길이가 모두 일치해야 집계되므로 이전 짧은 구간의 통과를 늘어난 구간의 통과로 재사용하지 않는다. 일반 완료 경로의 장면별 `quality.json`과 대체 편집의 `final-fidelity-reviews*.json`은 기록 형식이 다르다. 이 명령의 `--reviews`에는 후자의 최종 창 목록만 전달한다. 보고서만 집계하면 실제 디코딩 검증은 수행되지 않으며 `--video`가 필요하다.

공개 집계에는 원본 사진, 프롬프트 원문, 사용자 경로·ID를 넣지 않는다. 지표와 산출물의 SHA-256으로 어떤 파일을 측정했는지 연결한다. 현재 이 명령은 지표를 보고하며 출시 허용 여부를 자동 결정하지 않는다.
